# Диагностика

## Интерфейс не открывается

```bash
docker compose ps
docker compose logs --tail=200 api
curl --fail http://localhost:8000/health/ready
```

В локальном Compose веб-интерфейс обслуживается тем же контейнером API на `http://localhost:5173`. Если `health` работает, а `ready` нет, проверить PostgreSQL и применить миграции: `make db-upgrade`.

Ошибка о колонке `password_hash` после обновления означает, что образ уже новый, а схема базы ещё старая. Выполнить `make db-upgrade` и повторить запрос.

## Не удаётся войти

- новый пароль должен содержать не менее 10 символов;
- email при входе не зависит от регистра;
- успешный вход заменяет прежний bearer token, поэтому другая открытая сессия получит `401`;
- профиль, созданный до миграции `0004_user_passwords`, продолжает работать с уже сохранённым токеном, но не имеет пароля для повторного входа. Для локальных демонстрационных данных безопаснее создать новый профиль; публичных production-профилей до этой миграции быть не должно.

## Наблюдение сохранилось, но анализ недоступен

Это ожидаемая деградация: фотография и описание уже находятся в истории, а интерфейс показывает причину частичного сбоя. Повторное открытие карточки обновляет историю. Проверить:

```bash
docker compose logs --tail=200 api
docker compose logs --tail=200 outbox-worker
```

Без `PLANTGUARD_PLANTNET_API_KEY` используется локальная модель. Без LLM-настроек объяснение формируется детерминированно. Ни один из этих ключей не обязателен для базового сценария.

## Фотография перестала открываться

Подписанная ссылка действует ограниченное время. Обновить страницу или снова запросить `/history`. Если API возвращает `404`, проверить volume:

```bash
docker volume ls | grep plantguard
docker compose exec api find /var/lib/plantguard/photos -type f | head
```

Не удалять `plantguard_photo-data` отдельно от PostgreSQL: база и файлы должны резервироваться и восстанавливаться согласованно.

## Kafka или ksqlDB не готовы

```bash
docker compose ps kafka ksqldb outbox-worker
docker compose logs --tail=200 kafka ksqldb outbox-worker
make ksql-init
make test-streams
```

На машине с 4 ГБ RAM запуск всех сервисов может упираться в память. Для полного контура рекомендуется 6 ГБ. После временной недоступности Kafka outbox worker повторяет отправку и не теряет сохранённые API-события.

## Конфликт портов

Локально используются `5173`, `8000`, `8088`, `9092` и `5432`. Найти процесс на macOS/Linux можно через `lsof -nP -iTCP:<порт> -sTCP:LISTEN`. Либо остановить другой стек, либо изменить host-side port в `compose.yaml`.

## Чистый локальный запуск

Обычный перезапуск не удаляет данные:

```bash
docker compose down
docker compose up --build --detach --wait
make db-upgrade
make ksql-init
make smoke
```

`docker compose down --volumes` удаляет базу и фотографии без возможности восстановления. Использовать его только для намеренного сброса демонстрационных данных после резервной копии.

## Что приложить к issue

- точную команду или шаг интерфейса;
- ожидаемое и фактическое поведение;
- `X-Request-ID` ответа;
- версии Docker, Python и Node.js;
- релевантный фрагмент логов без токенов, паролей, API-ключей и пользовательских фотографий.
