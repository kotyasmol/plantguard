# Архитектура PlantGuard

## Принципы

1. Результат модели является версионируемым наблюдением, а не окончательным фактом.
2. Каждая рекомендация содержит исходные признаки, уровень уверенности и версию правил.
3. События неизменяемы; исправления пользователя записываются отдельными событиями.
4. Изображения хранятся в объектном хранилище, а в Kafka передаются ссылки и метаданные.
5. При недоступности внешней модели система сохраняет наблюдение и возвращает безопасный статус ожидания.

## Компоненты

### Web application

Клиентское приложение отвечает за создание карточки растения, загрузку снимков, ввод условий ухода и отображение истории. Для повторной съёмки планируется режим совмещения нового кадра с предыдущим.

### Application API

API хранит основные сущности и управляет сценарием оценки состояния:

- `Plant` — подтверждённый или предполагаемый вид растения;
- `Observation` — фотография, текст и показатели среды в определённый момент;
- `CareEvent` — полив, подкормка, пересадка или изменение расположения;
- `Assessment` — структурированный результат анализа;
- `Recommendation` — объяснимое действие с ограничениями и уровнем уверенности.

### Data Integration

Kafka используется как журнал событий между прикладным API, сервисом анализа и обработчиком уведомлений. ksqlDB выполняет потоковые преобразования:

- приводит события к ключу `plant_id`;
- объединяет наблюдения с последними показателями среды;
- рассчитывает оконные агрегаты;
- формирует предупреждения о заданных неблагоприятных условиях;
- подготавливает данные для повторной оценки состояния.

Основные топики:

| Топик | Назначение |
| --- | --- |
| `plant.observations.v1` | Новые наблюдения пользователя |
| `plant.care-events.v1` | События ухода |
| `plant.environment-readings.v1` | Ручные или сенсорные показатели среды |
| `plant.identification-results.v1` | Кандидаты вида растения |
| `plant.assessment-results.v1` | Оценки состояния и рекомендации |
| `plant.alerts.v1` | Предупреждения, созданные потоковыми правилами |

### Data Mining

Слой анализа состоит из независимых адаптеров:

- идентификация вида растения по изображению;
- извлечение визуальных признаков состояния;
- проверка сопоставимости двух фотографий;
- извлечение симптомов из пользовательского текста;
- политика объединения сигналов;
- генерация объяснения по структурированным фактам.

Такое разделение позволяет заменять модели без изменения прикладного API и тестировать логику принятия решений на фиксированных результатах моделей.

## Поток первого наблюдения

1. Клиент получает ссылку для загрузки фотографии.
2. После загрузки API создаёт наблюдение и публикует `plant.observations.v1`.
3. Сервис анализа формирует кандидатов вида и признаки состояния.
4. API объединяет результаты с доступной историей и условиями содержания.
5. Политика принятия решений определяет уровень риска и необходимость уточнения.
6. Клиент показывает пользователю результат и сохраняет подтверждение или исправление.

## Поток повторного наблюдения

1. Пользователь делает новый снимок по подсказке приложения.
2. Сервис анализа оценивает сопоставимость снимков.
3. Если снимки сопоставимы, рассчитывается изменение выбранных признаков.
4. События ухода и показатели среды добавляются к контексту временного интервала.
5. Формируется новая оценка, которая ссылается на предыдущую.

## Границы ответственности

- LLM не принимает итоговое решение самостоятельно и не получает права придумывать факты.
- Пороговые значения и правила риска хранятся отдельно от текста объяснения.
- Клиент не вычисляет диагноз и не интерпретирует уверенность модели.
- ksqlDB обрабатывает потоковые факты, а долговременное состояние хранится в PostgreSQL.
