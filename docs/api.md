# REST API

Интерактивная OpenAPI-схема доступна по `/docs`, машинная — по `/openapi.json`. Все прикладные маршруты имеют префикс `/api/v1`.

## Авторизация

Регистрация:

```http
POST /api/v1/users
Content-Type: application/json

{
  "display_name": "Екатерина",
  "email": "katya@example.com",
  "password": "long-private-password"
}
```

Повторный вход выполняется через `POST /api/v1/sessions` с `email` и `password`. В обоих случаях ответ содержит `access_token`. Пароли сохраняются только в виде salted PBKDF2-SHA256 hash; успешный повторный вход ротирует токен и завершает прежнюю сессию.

Защищённые запросы передают:

```http
Authorization: Bearer <access_token>
```

`GET /api/v1/users/me` возвращает профиль, `DELETE /api/v1/users/me` необратимо удаляет профиль, растения, историю и связанные фотографии.

## Основной сценарий

1. `POST /api/v1/plants` — создать карточку растения.
2. `POST /api/v1/plants/{plant_id}/observations` — сохранить фотографию, описание и необязательные показатели среды.
3. `POST .../{observation_id}/identify` — получить до пяти кандидатов вида.
4. `POST .../{observation_id}/assess` — выполнить сводную оценку СППР.
5. `PATCH /api/v1/plants/{plant_id}/species` — подтвердить выбранный вид.
6. `POST /api/v1/plants/{plant_id}/care-events` — записать действие по уходу.
7. `GET /api/v1/plants/{plant_id}/history` — получить карточку, снимки, уход и оценки.

Фотография в наблюдении отправляется как `multipart/form-data`. Поддерживаются JPEG, PNG и WebP до настроенного лимита; MIME-тип сверяется с фактическим содержимым. `humidity_pct` допускает значения `0..100`, `temperature_c` — `-50..70`.

## Ручные показания и уведомления

Для всех четырёх маршрутов нужен bearer-токен владельца.

| Запрос | Результат |
| --- | --- |
| `POST /api/v1/plants/{plant_id}/environment-readings` | Принимает JSON, например `{"temperature_c": 22.5, "humidity_pct": 8}`. Достаточно одного показателя. Температура от −50 до 70 °C, влажность от 0 до 100%, точность до двух знаков после запятой. Ответ `201` содержит ID показания и растения, серверное время `occurred_at` и оба показателя. Пропущенное значение возвращается как `null`. |
| `GET /api/v1/plants/{plant_id}/environment-readings` | Последние показания по убыванию времени. Параметр `limit` принимает от 1 до 100, по умолчанию 30. |
| `GET /api/v1/alerts` | Уведомления по растениям владельца, начиная с новых. Для непрочитанных передайте `?unread=true`. Каждый элемент содержит `id`, `plant_id`, `alert_code`, `severity`, `occurred_at` и `acknowledged_at`. До прочтения `acknowledged_at` равен `null`. |
| `POST /api/v1/alerts/{alert_id}/acknowledge` | Возвращает обновлённое уведомление и статус `200`. Повторный запрос сохраняет время первой отметки. |

Уведомления появляются асинхронно после обработки показания в ksqlDB. Запрос к чужому растению или уведомлению возвращает `404`.

## Аналитические маршруты

| Метод и путь | Результат |
|---|---|
| `POST .../{observation_id}/analyze-visual` | видимые признаки и confidence |
| `POST .../{observation_id}/analyze-text` | признаки из сохранённого описания |
| `POST .../{current_id}/compare/{reference_id}` | сопоставимость снимков и метрики |
| `POST .../{current_id}/dynamics/{reference_id}` | тренд, изменения признаков и уход между снимками |
| `POST .../{observation_id}/assess` | риск, evidence, missing inputs, действия и объяснение |

Оценка является поддержкой решения, а не медицинским или фитопатологическим диагнозом. При недостаточной уверенности API возвращает `needs_review`, `requires_more_data` или `requires_species_confirmation` вместо принудительного вывода.

## Фотографии

`read_url` в истории — короткоживущая подписанная ссылка. Она привязана к HTTP-методу и ключу объекта. После истечения ссылки клиент повторно запрашивает историю и получает новую. Ответ фотографии запрещает MIME-sniffing и публичное кеширование.

Отдельные низкоуровневые маршруты `POST /api/v1/photos`, `GET /api/v1/photos/{storage_key}` и `DELETE /api/v1/photos/{storage_key}` используются smoke-тестом хранилища.

## Ошибки

API использует стандартные HTTP-коды:

- `401` — отсутствующий, истёкший или заменённый токен;
- `403` — недействительная подписанная ссылка;
- `404` — объект отсутствует либо принадлежит другому пользователю;
- `409` — конфликт состояния, например уже зарегистрированный email;
- `413` — превышен размер файла или число пикселей;
- `415` — неподдерживаемый media type;
- `422` — ошибка полей или повреждённое изображение.

Каждый ответ содержит `X-Request-ID`. Его следует прикладывать к журналам при диагностике.

## Системные маршруты

- `GET /health` — liveness процесса;
- `GET /health/ready` — проверка соединения с PostgreSQL;
- `GET /metrics` — Prometheus-совместимые HTTP-счётчики.
