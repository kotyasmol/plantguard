# Тестирование и критерии приёмки

PlantGuard использует четыре уровня проверок: unit-тесты правил и моделей, API-интеграцию с временной базой и файловым хранилищем, frontend-тесты пользовательских сценариев и системные проверки PostgreSQL/Kafka/ksqlDB.

## Быстрый прогон

После `make bootstrap`:

```bash
make lint
make test
make test-coverage
make build
```

`make test-coverage` завершится ошибкой, если суммарное покрытие Python-кода опустится ниже 85% либо frontend — ниже 80% statements, 70% branches, 80% functions или 85% lines. Отчёты выводятся в терминал; JSON-summary frontend-покрытия создаётся в игнорируемом каталоге `apps/web/coverage`.

## Инфраструктурные проверки

Для следующих команд нужен запущенный Docker Engine:

```bash
make test-migrations
make test-streams
```

- `test-migrations` применяет все Alembic-миграции к одноразовому PostgreSQL, сверяет таблицы и ограничения, проверяет каскадное удаление, откатывает схему до `base` и повторно применяет её;
- `test-streams` поднимает Kafka и ksqlDB, создаёт потоковые объекты и проверяет дедупликацию, event-time окно, запоздавшее событие и формирование предупреждения.

После локального запуска полного стека выполняется smoke-проверка:

```bash
make smoke
```

Она проверяет UI, readiness API, загрузку/чтение/удаление фотографии, ksqlDB и наличие обязательных потоков и таблиц.

## Матрица приёмки

| Требование | Автоматическая проверка |
|---|---|
| Регистрация, вход и ротация токена | `test_registered_user_can_sign_in_again`, frontend workflow |
| Изоляция данных владельцев | `test_users_cannot_access_or_modify_each_others_plants` |
| Безопасная загрузка JPEG/PNG/WebP | `test_api.py`, `test_photo_storage.py` |
| Сохранение фото и истории после перезапуска | `test_plant_history_survives_api_restart` |
| Распознавание и ручное подтверждение вида | `test_identification_*`, frontend workflow |
| Image- и text-анализ | `test_visual.py`, `test_text.py`, API integration |
| Объяснимая СППР без выдуманных диагнозов | `test_policy.py`, `test_explanations.py`, `test_llm.py` |
| Сравнение снимков и динамика | `test_comparison.py`, `test_dynamics.py`, API integration |
| Сохранение при частичном отказе модели | frontend test `keeps a saved observation visible…` |
| Transactional outbox и повторная отправка | `test_outbox.py` |
| Kafka + ksqlDB | `scripts/test_stream_processing.py` |
| Миграции вперёд/назад | `services/api/migration_test.py` |
| Production-сборка | `make build`, сборка Docker-образа |

## Ручной smoke-flow

Перед релизом дополнительно пройти в desktop- и mobile-размере окна:

1. создать профиль с паролем;
2. выйти и войти повторно;
3. добавить растение;
4. загрузить корректную фотографию и описание;
5. убедиться, что результат содержит уверенность, объяснение и оговорку «не диагноз»;
6. подтвердить вид вручную;
7. добавить действие по уходу;
8. загрузить второй снимок и открыть фотопрогресс;
9. проверить переходы между снимками клавишами `←`, `→`, закрытие через `Escape`;
10. перезапустить контейнеры и убедиться, что история сохранилась.

Недоступность внешнего LLM или Pl@ntNet не должна блокировать сохранение наблюдения: используются локальные адаптеры, а интерфейс сообщает о частично недоступном анализе.

## Правило для изменений

Исправление дефекта сначала воспроизводится тестом. Новая функциональность должна иметь хотя бы один позитивный и один ошибочный сценарий на наиболее близком уровне. Изменение JSON-события требует обновления схемы в `contracts/events`, примера и contract-теста.
