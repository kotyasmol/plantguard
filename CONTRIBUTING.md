# Участие в разработке

## Подготовка

```bash
git clone https://github.com/kotyasmol/plantguard.git
cd plantguard
make bootstrap
cp .env.example .env
```

Для изменения API, mining или frontend достаточно локального toolchain. Для миграций, Kafka/ksqlDB и полного smoke-flow нужен Docker.

## Рабочий процесс

1. Создайте отдельную ветку от актуального `main`.
2. Делайте небольшие тематические коммиты с сообщениями вида `feat:`, `fix:`, `test:`, `docs:`.
3. Добавьте тест, воспроизводящий новое поведение или исправленный дефект.
4. Перед pull request выполните:

```bash
make lint
make test-coverage
make build
```

При изменении миграций или потоковой логики также выполните `make test-migrations` и `make test-streams`.

## Требования к изменениям

- не ослаблять coverage-gates и валидацию загрузок;
- не добавлять диагнозы или рекомендации, не подтверждённые evidence-кодами;
- не логировать bearer tokens, пароли, API-ключи и содержимое фотографий;
- сохранять обратную совместимость версионированных событий либо выпускать новую версию topic/schema;
- указывать источник, лицензию и разрешение для каждого изображения датасета;
- не коммитить `.env`, production secrets, runtime volumes и пользовательские снимки.

Архитектурные решения стоит описывать в `docs/architecture.md`, пользовательские изменения — в README или профильном документе. О найденных уязвимостях следует сообщать по процедуре из `SECURITY.md`, а не через публичный issue.
